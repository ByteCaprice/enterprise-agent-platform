# 平台建设路线图

平台当前定位为**生产级框架原型，尚未达到生产就绪**。基础执行、治理和交付能力已经交付，下一阶段以边界收敛、契约补全和实际场景验证为主，不以不断增加功能为目标。当前实现见[功能与架构](overview.md)；公开/私有内容边界见[文档政策](repository-policy.md)。

## 建设原则

- Enterprise AI Platform 使用独立的接口、领域模型、数据归属和部署契约；复用组件须符合这些契约。
- 先理清依赖和数据所有权，再扩展框架；不通过简单改名或搬目录冒充解耦，不擅自操作持久环境。
- Task / TaskAttempt 是执行和最终结果的权威；Workflow、Agent、模型和工具记录是从属证据，Callback 投递有独立生命周期。
- 授权在实际模型、工具和其他受控资源调用处执行。已发布版本不可静默覆盖，历史执行始终指向固定版本。
- 外部操作结果未知时不自动假定失败或重放；业务写操作需要明确的幂等、结果查询或人工处置机制。
- 以可运行的能力闭环和必要验证推进，不以原型页面、占位接口或模拟成功代替实现。

## 已交付基础与边界

目前已有版本化能力、身份和资源 Grant、持久 Task / Attempt、从固定 Workflow DSL 编译的不可变运行期计划、受治理的 Agent Runtime、模型与只读工具 Gateway、Callback、基础评测和业务反馈。编译计划不作为制品持久化。已受理请求的关联元数据与 Task 执行状态分离；同步/异步是交付偏好，不改变执行授权。任务详情可分别分页观察接入请求与 Callback 交付，交付查询按 Task 的实时读取范围授权且不暴露端点配置或租约。纯规则 Workflow 支持通过显式新 Task 复用经校验的检查点。

这些基础不等于完整产品。当前仅内置 Pi 运行适配器；完整用户/成员 RBAC、持久等待与审批、外部写操作以及包含外部调用的恢复仍未交付。此类能力不能只增加接口，必须先定义身份、状态所有权、授权、幂等和结果确认等业务契约。

## 下一阶段重点

1. **收敛用例边界**：发布命令、只读制品解析、Prompt 渲染与计划查询已分开；继续按实际用例分离存储事务和业务规则，避免通用 Manager 或跨模块私有方法成为隐式共享内核。
2. **补全请求到交付的可追踪性**：以稳定关联元数据连接 Gateway Request、Task 和交付记录，并形成清晰的运营查询口径。
3. **明确扩展契约**：在实现等待/审批、User RBAC、受控写 IO 或更广恢复能力前，先约定权限模型、持久状态、幂等与故障后的结果确认。
4. **按实际使用验证**：围绕具体能力闭环补齐必要运营指标、质量口径和客户数据治理，不预先假定通用策略适用于所有部署。

进展以可验证、可安全使用的契约为准；不把占位接口或模板配置视为交付。

## 需要另行确认的事项

以下事项不阻塞通用框架设计，但不能以示例或历史默认值代替实际决策：

- 企业身份系统、组织结构和角色映射。
- 模型供应商、网络出口、定价、预算和成本核算规则。
- 业务写操作的授权、审批、幂等、结果查询及对账规则。
- 客户数据的分类、加密、留存、导出和物理删除要求。
- 多个反馈提交人之间的最终采纳规则，以及业务质量指标口径。

## 总体验收

按功能依赖逐步验证：Agent 和确定性 Workflow 的完整调用；异步结果交付与接收方去重；跨 Worker 并发限制；进程异常后的安全收敛；跨项目授权与审计；能力、Prompt、模型、工具及 Skill 的版本追踪；以及分别统计技术完成、业务采纳和质量评测结果。

在实际身份、供应商、网络、数据和业务策略完成确认与验证之前，不将平台标记为生产就绪。
